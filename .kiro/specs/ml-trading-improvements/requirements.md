# Requirements Document

## Introduction

This feature adds three major improvements to the IG Scalper trading bot to reduce false signals, avoid adverse market conditions, and properly size positions based on actual risk. The improvements are: (1) an ML-based directional filter using logistic regression, (2) a volatility regime filter based on ATR percentiles, and (3) risk-per-trade position sizing that replaces the current fixed invest_per_trade approach.

## Glossary

- **ML_Filter**: A logistic regression model that predicts next-bar price direction using technical features (RSI, ATR ratio, SMA ratio, lagged returns) derived from OHLC data
- **Volatility_Filter**: A pre-signal gate that blocks trading when the ATR/price ratio falls outside configurable percentile bounds of recent ATR history
- **Position_Sizer**: A module that calculates trade size based on account equity, configured risk percentage, actual stop distance, and instrument pip value
- **ATR**: Average True Range — a measure of price volatility over a configurable period
- **ATR_Ratio**: The ratio of current ATR to current price (ATR / close), expressing volatility as a percentage of price
- **ATR_Percentile**: The rank of the current ATR_Ratio within a rolling window of historical ATR_Ratio values
- **Signal**: A trade recommendation produced by the AI Pattern Recognizer or FVG strategy containing direction, stop distance, and take-profit distance
- **Prediction_Probability**: The ML_Filter output value between 0.0 and 1.0 representing confidence in bullish direction
- **Rolling_Window**: A fixed-length sliding window of historical bars used for training or percentile calculation
- **Account_Equity**: The current total account balance retrieved from the IG API
- **Stop_Distance**: The distance in points between entry price and stop loss for a specific trade
- **Pip_Value**: The monetary value per point of movement for one unit of deal size on a given instrument

## Requirements

### Requirement 1: ML Directional Filter — Model Training

**User Story:** As a trader, I want the bot to train a lightweight ML model on historical price features at startup, so that it can predict next-bar direction and filter out low-quality signals.

#### Acceptance Criteria

1. WHEN the trading bot starts, THE ML_Filter SHALL train a logistic regression model on the most recent Rolling_Window of historical OHLC bars (default: 500 bars)
2. THE ML_Filter SHALL use the following features for training: 14-period RSI, ATR_Ratio (14-period ATR divided by close price), SMA ratio (close divided by 50-period SMA), and 1-bar, 3-bar, and 5-bar lagged returns
3. THE ML_Filter SHALL label each training sample as 1 (bullish) if the next bar's close is higher than the current bar's close, and 0 (bearish) otherwise
4. THE ML_Filter SHALL normalize all features using z-score standardization before training
5. IF the available historical data contains fewer than 100 bars, THEN THE ML_Filter SHALL log a warning and disable itself until sufficient data accumulates
6. WHERE a pre-trained model file exists at the configured path, THE ML_Filter SHALL load the model from disk instead of retraining

### Requirement 2: ML Directional Filter — Signal Filtering

**User Story:** As a trader, I want the ML model to confirm or reject signals from the pattern/FVG strategy, so that the bot only takes trades where both the technical signal and ML prediction agree on direction.

#### Acceptance Criteria

1. WHEN a Signal is generated by the AI Pattern Recognizer or FVG strategy, THE ML_Filter SHALL compute a Prediction_Probability for the current bar's features
2. WHEN the Signal direction is BUY, THE ML_Filter SHALL confirm the signal only if the Prediction_Probability exceeds the configured threshold (default: 0.55)
3. WHEN the Signal direction is SELL, THE ML_Filter SHALL confirm the signal only if (1.0 minus Prediction_Probability) exceeds the configured threshold (default: 0.55)
4. IF the ML_Filter rejects a Signal, THEN THE ML_Filter SHALL log the rejection reason including the signal direction, Prediction_Probability, and threshold value
5. WHILE the ML_Filter is disabled (insufficient data or missing model), THE trading bot SHALL pass all signals through without ML filtering

### Requirement 3: ML Directional Filter — Periodic Retraining

**User Story:** As a trader, I want the ML model to retrain periodically using recent data, so that it adapts to changing market conditions.

#### Acceptance Criteria

1. WHEN the configured retrain interval elapses (default: 168 hours / 1 week), THE ML_Filter SHALL retrain the model on the most recent Rolling_Window of bars
2. THE ML_Filter SHALL save the retrained model to disk at the configured model path after each successful retraining
3. IF retraining fails due to insufficient data or computation error, THEN THE ML_Filter SHALL continue using the previous model and log the error
4. THE ML_Filter SHALL record the timestamp of the last successful training in the model metadata

### Requirement 4: ML Filter Configuration

**User Story:** As a trader, I want to configure ML filter parameters via YAML settings, so that I can tune behavior without code changes.

#### Acceptance Criteria

1. THE trading bot SHALL read ML_Filter configuration from the `ml_filter` section of `config/settings_ai.yaml`
2. THE ML_Filter configuration SHALL include: enabled (boolean), probability_threshold (float), rolling_window_bars (integer), retrain_interval_hours (integer), model_path (string), and model_type (string: "logistic_regression" or "random_forest")
3. WHERE `ml_filter.enabled` is set to false, THE trading bot SHALL skip ML filtering entirely and pass all signals through

### Requirement 5: Volatility Regime Filter — ATR Percentile Calculation

**User Story:** As a trader, I want the bot to measure current volatility relative to recent history, so that it can identify abnormal market conditions.

#### Acceptance Criteria

1. THE Volatility_Filter SHALL compute the ATR_Ratio for the current bar using a 14-period ATR divided by the current close price
2. THE Volatility_Filter SHALL maintain a rolling history of ATR_Ratio values over a configurable lookback period (default: 100 bars, representing approximately 20 periods of 5-minute data)
3. THE Volatility_Filter SHALL compute the percentile rank of the current ATR_Ratio within the rolling history
4. IF the rolling history contains fewer than 20 ATR_Ratio values, THEN THE Volatility_Filter SHALL allow trading and log that insufficient history is available for percentile calculation

### Requirement 6: Volatility Regime Filter — Trading Gate

**User Story:** As a trader, I want the bot to skip trading when volatility is abnormally high (market chaos) or abnormally low (no opportunity), so that it avoids unfavorable conditions.

#### Acceptance Criteria

1. THE Volatility_Filter SHALL block signal generation when the current ATR_Percentile is above the configured upper bound (default: 80th percentile)
2. THE Volatility_Filter SHALL block signal generation when the current ATR_Percentile is below the configured lower bound (default: 20th percentile)
3. WHEN the Volatility_Filter blocks trading due to high volatility, THE Volatility_Filter SHALL log the blocking reason as "volatility too high" with the current ATR_Ratio, ATR_Percentile, and upper bound
4. WHEN the Volatility_Filter blocks trading due to low volatility, THE Volatility_Filter SHALL log the blocking reason as "volatility too low" with the current ATR_Ratio, ATR_Percentile, and lower bound
5. THE Volatility_Filter SHALL run before signal generation in the trading loop to avoid unnecessary computation when conditions are unfavorable

### Requirement 7: Volatility Filter Configuration

**User Story:** As a trader, I want to configure volatility filter parameters via YAML settings, so that I can adjust thresholds for different market conditions.

#### Acceptance Criteria

1. THE trading bot SHALL read Volatility_Filter configuration from the `volatility_filter` section of `config/settings_ai.yaml`
2. THE Volatility_Filter configuration SHALL include: enabled (boolean), atr_period (integer), lookback_bars (integer), lower_percentile (float), and upper_percentile (float)
3. WHERE `volatility_filter.enabled` is set to false, THE trading bot SHALL skip volatility filtering entirely

### Requirement 8: Risk-Per-Trade Position Sizing — Size Calculation

**User Story:** As a trader, I want each trade sized to risk exactly a configured percentage of my current account equity, so that position size adapts to both account growth and trade-specific stop distance.

#### Acceptance Criteria

1. WHEN a confirmed Signal is ready for execution, THE Position_Sizer SHALL calculate deal size using the formula: size = (Account_Equity × risk_percentage) / (Stop_Distance × Pip_Value)
2. THE Position_Sizer SHALL retrieve current Account_Equity from the IG API account summary
3. THE Position_Sizer SHALL use the actual Stop_Distance from the confirmed Signal (after S/R adjustment and market rules enforcement)
4. THE Position_Sizer SHALL use the Pip_Value obtained from the IG market details for the specific instrument
5. IF the calculated size is below the IG minimum deal size for the instrument, THEN THE Position_Sizer SHALL reject the trade and log that risk budget is insufficient for the minimum position size
6. THE Position_Sizer SHALL round the calculated size down to the nearest valid size step (0.1 for most instruments)

### Requirement 9: Risk-Per-Trade Position Sizing — Equity Management

**User Story:** As a trader, I want the position sizer to use live account equity so that risk scales with account performance.

#### Acceptance Criteria

1. THE Position_Sizer SHALL refresh Account_Equity from the IG API at configurable intervals (default: every 5 minutes)
2. IF the IG API equity fetch fails, THEN THE Position_Sizer SHALL use the last successfully retrieved equity value and log a warning
3. THE Position_Sizer SHALL use the account balance field (not available-to-deal) as the equity basis for calculation

### Requirement 10: Position Sizing Configuration

**User Story:** As a trader, I want to configure risk percentage and position sizing parameters via YAML settings, so that I can adjust risk tolerance without code changes.

#### Acceptance Criteria

1. THE trading bot SHALL read Position_Sizer configuration from the `risk` section of `config/settings_ai.yaml`
2. THE Position_Sizer configuration SHALL include: risk_pct_per_trade (float, default: 2.0), equity_refresh_interval_seconds (integer, default: 300), and use_dynamic_sizing (boolean, default: true)
3. WHERE `risk.use_dynamic_sizing` is set to false, THE Position_Sizer SHALL fall back to the existing fixed `invest_per_trade` sizing logic
4. THE Position_Sizer SHALL cap maximum position size at a configurable multiple of the minimum deal size (default: 50x) to prevent oversized positions from calculation errors

### Requirement 11: Integration with Existing Trading Loop

**User Story:** As a trader, I want all three improvements integrated into the existing trading loop in the correct order, so that filtering and sizing happen at the right stages.

#### Acceptance Criteria

1. THE trading bot SHALL apply the Volatility_Filter before calling the strategy's `on_bar()` method
2. THE trading bot SHALL apply the ML_Filter after receiving a Signal from the strategy and before order execution
3. THE trading bot SHALL apply the Position_Sizer after all filters have confirmed the Signal and before placing the order with IG
4. THE trading bot SHALL log a summary at each filter stage showing: filter name, outcome (pass/block), and key metrics
5. IF all filters pass but Position_Sizer rejects due to insufficient risk budget, THEN THE trading bot SHALL skip the trade and log the reason without entering cooldown
